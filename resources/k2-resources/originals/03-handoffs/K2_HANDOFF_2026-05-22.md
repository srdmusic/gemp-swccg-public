## 4. The V-tag system

Every rule change gets a V-tag: V21, V22, V67ai, V67bh, etc. The tag lives as a comment block in code AND as an entry in `AI_VERSION_HISTORY.md`. `git blame` on any AI file shows the V-tag history with dates.

**Three places to look up what a V-tag means:**

1. `AI_CHANGELOG.md` — user-facing summary, organized by category
2. `AI_VERSION_HISTORY.md` — V-tag-by-V-tag chronological detail
3. `Rando_AI_Rule_Audit.xlsx` — K2-built audit with 200+ rules, finds contradictions

The xlsx is especially valuable. It has sheets:

- `All Rules` — every V-tag with category, problem, fix, status
- `Audit Findings` — 50+ identified contradictions / dead rules / detection-path mismatches
- `By Category` — same data sliced by category
- `Pre-Tag Era` — pre-V21 commits

**Always consult the xlsx before adding a new rule** — it prevents writing a rule that contradicts an existing one.

## 6. Key architectural concepts to absorb

### DeckOracle is the source of truth

`DeckOracle.java` catalogs every card in your deck at game start (`DeckCard` records with title, blueprint, category, subtype, icons, game text). It tracks each card's `currentZone` as the game progresses.

**Two query flavors** (this distinction matters):

| Method | Behavior |
|--------|----------|
| `hasFilterMatchInReserve(game, playerId, Filter)` | **Type-aware** — uses CardCategory/CardSubtype/Icon/Keyword via SWCCG Filter semantics |
| `getCardsByCategory(CardCategory, Zone)` | Type-aware count |
| `validatePull(Zone, String[] keywords)` | **Title-substring** — literal string match against card titles |
| `hasTargetInReserve(String... keywords)` | Title-substring |
| `resolveCommonNounToFilter(noun)` | Maps "location"/"site"/"weapon" etc to typed Filter |

The V123/V123-DEPLOY bug was using title-substring (`validatePull`) for a category noun ("location"). Should have used filter (`hasFilterMatchInReserve`). **Standing rule from `feedback_card_search_by_type_not_text.md`: "Always search by CardCategory / CardSubtype / Icon / Persona / Keyword / Filters — NEVER substring-match generic nouns against card titles."**

### SWCCG type taxonomy

```
CardCategory (top-level)
├── LOCATION       ─ broad, includes:
│   ├── CardSubtype.SITE
│   ├── CardSubtype.SYSTEM
│   └── CardSubtype.SECTOR
├── CHARACTER
├── STARSHIP
├── VEHICLE
├── WEAPON
├── DEVICE
├── INTERRUPT
├── EFFECT
├── OBJECTIVE
└── DEFENSIVE_SHIELD

Plus orthogonal classifications:
├── Icon (Sith, Cloud City, Episode I, Battleground, Force, etc.)
├── Keyword (Senator, Jedi Master, Pilot, Bounty Hunter, etc.)
├── Persona (Vader, Luke, Han, etc. — uniqueness tracking)
└── Species (Neimoidian, Wookiee, etc.)
```

When in doubt about a card's type, check its blueprint via `gameState.findCardById(cardId).getBlueprint()`.

### Detection-path mismatches (recurring pattern)

The most common architectural bug in this codebase: a rule lives in one evaluator, but the engine routes the decision through a different evaluator.

**Examples:**

| Original | Routes through | Mirror added |
|----------|----------------|--------------|
| V99 in `DeployEvaluator` | Generic "Deploy" → `CardSelectionEvaluator` location-pick | V99-CS |
| V88 ditto | ditto | V88-LORE |
| V89 ditto | ditto | V89-CS |
| V83 ditto | ditto | (already covered by V88-CS) |
| V86 ditto | ditto | V121 (this session) |
| V90 ditto | ditto | V122 (this session) |
| V51 in `evaluateDefensiveShieldSelection` | K&D mixed-stack → `evaluateUnknown` | V112 (this session) |
| V105/V107 ditto | ditto | V117 (this session, partial) + V124 (parent action) |
| V101 in `evaluateForceLoss` | Battle-end combined → `evaluateForceLossOrForfeit` | V119 (this session) |
| V66 (1st copy) in `ActionTextEvaluator` | DeployEvaluator's own V66 copy | V123-DEPLOY (this session) |

**When adding a new rule:** ALWAYS check if the same decision could be routed through a sibling evaluator. If yes, add the mirror in the same commit.

## 8. Debugging lessons from this session

These are the bigger lessons I want to carry forward — Steve called these out explicitly when frustrated:

### Lesson 1: Code that compiles is NOT code that works

I shipped V115, V117, V118, V119, V120, V121, V122 thinking they were "done" because the build passed. Steve played a game and reported the same symptoms. Log evidence:

```
docker exec gemp_swccg_app_1 grep -oE "V[0-9]+[a-z]*" /root/nohup.out | sort -u
# Returned: V100, V101, V102, V104, V105, V106, V107, V108, V109, V113, V116, V21-V91...
# Missing: V115, V117, V118, V119, V120, V121, V122
```

Not a single new V-tag from this session fired. They all had bugs:
- V117 was in the wrong code path (shield decisions actually route through `evaluateDefensiveShieldSelection`, not `evaluateUnknown`)
- V120 had `.equals()` vs `.contains()` mismatch
- V123 had a duplicate copy in DeployEvaluator I missed

**Rule for future sessions:** after every restart, immediately `docker exec gemp_swccg_app_1 grep "V12X" /root/nohup.out` to verify the new V-tag actually logs. If it doesn't fire, the rule isn't shipped — it's wishful thinking.

### Lesson 2: When user says "X is broken," the data tells you what's actually wrong

Steve said "Hunt Down sites still not deploying." Initial instinct: blame my recent changes. Actual answer from logs:

```
[ActionText] Deploy a location from Reserve Deck: -9899.0
  V116 RESERVE OPTION: +100
  V66 MEMORY: No match for 'location' in RESERVE_DECK — search will FAIL (-9999)
```

V66 (a much older rule, not from this session) was the actual blocker. It treated "location" as a card title. The fix was nowhere near my recent changes.

**Rule:** always grep logs for the specific action FIRST. Don't assume your recent code is the cause.

### Lesson 3: The user is right when they say something is wrong

Steve said "I just played and Vader got two lightsabers" — when I had FIVE rules (V67ay, V67aq, V67ar, V70, V115) supposedly blocking this. Trust the report. The fix was V120 (the SIXTH gap nobody had thought of) plus V125 (a bug IN V120). The five existing rules all had blind spots.

### Lesson 4: Side-symmetry matters

Cards usually come in light + dark pairs. Knowledge And Defense (Dark) has Anger, Fear, Aggression (Light) as a structural mirror. If a rule applies to one, it likely applies to both. V124 currently only catches "knowledge and defense" — Steve flagged AFA as the next gap.

### Lesson 5: The "audit findings" xlsx is gold

The K2-built `Rando_AI_Rule_Audit.xlsx` flagged "V90 detection-path mismatch" weeks before this session. We addressed it with V122 — same pattern as V99-CS. The xlsx categories worth consulting before every rule add:

1. Direct contradictions
2. Score magnitude inflation
3. Dead or superseded rules
4. Hard-block stacking
5. **Detection-path mismatches** ← most common architectural bug
6. Card-name hardcoding regressions
7. Side-symmetry gaps
8. Turn-window assumptions
9. Replay-specific overfitting

## 13. Game rules — where to learn the game itself

The codebase IS the rule engine, but Steve added a full rules corpus at `docs/`
(2026-05-22). The local K2 should read this to actually understand SWCCG before
making strategy calls — it's the difference between knowing what a `Filter` is
called and knowing why a player would deploy Vader's Castle in the first place.

### Recommended reading order for a fresh K2

1. **`.claude/skills/gemp-swccg-memory/references/game-mechanics.md`** (~190 lines)
   The quick-start summary derived from the codebase. Phases, card types,
   zones, force mechanics, battle mechanics. Read this first — it's the
   index card.

2. **`docs/SWCCG_BeginnersRulebook_v2.md`**
   The official Decipher entry-level rulebook. Read this to understand WHY
   the game works the way it does — Light vs Dark, life force depletion as
   win condition, drains vs battles vs force loss.

3. **`docs/SWCCG_AdvancedRulebook_2023.md`**
   The modern canonical rulebook. This is the deep dive — every edge case,
   timing rule, and clarification.

4. **`docs/SWCCG_Glossary_v2_1998.md` + `docs/SWCCG_GlossarySupplement_2002.md`**
   Definitive terminology. Look up any unfamiliar SWCCG word here before
   asking. "Drain", "presence", "uncontrollable", "immune to alter" —
   these all have precise meanings.

5. **`docs/SWCCG_SampleGame.md`**
   A walkthrough of an actual game. Best way to see all the rules in
   motion.

### Reference (read on-demand, don't pre-load)

- **`docs/PC_*.md`** — Players Committee modern clarifications. Read the
  one matching the deck you're analyzing (Hoth deck → `PC_Hoth_Energy_Shield_Rules.md`,
  Dagobah → `PC_Dagobah_Rules.md`, etc.). 11 of these covering Cave,
  Dagobah, Asteroid, Bluff, Jedi Tests, Podracers, Admirals Orders, Trench,
  Creature, Death Star II sectors, Hoth energy shield.

- **`docs/SWCCG_Expansion_*.md`** — per-expansion specific rules. 15 files
  (Cloud City, Coruscant, Dagobah, Death Star II, Empire Strikes Back
  2-Player, Endor, Enhanced Premiere, Hoth, Jabba's Palace, Reflections II,
  Reflections III, Tatooine, Theed Palace, A New Hope). Read the expansion
  matching the cards in play.

  Original-era clarifications. Useful for older cards.
- **`docs/SWCCG_CardList_3.3.md`** — card index.
- **`docs/pdf/`** — original PDFs for anything missing from the markdown.

### Token-efficiency tip for the local K2

Pre-load only #1 (`game-mechanics.md`, ~190 lines). For everything else,
grep on-demand: when an unfamiliar mechanic comes up, `grep -l <term> docs/`
